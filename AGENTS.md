# @asl-19/string-scripts

`@asl-19/string-scripts`: CLI tools (and the functions behind them) for converting strings JSON files to/from CSV for translators, and syncing strings JSON files. See [README.markdown](README.markdown) for usage.

## Commands

```sh
npm run dev-lint-test    # npm install, then type check, ESLint, Prettier, Vitest, publint, attw
npm run build-lint-test  # build, then the same checks (what CI and prepublishOnly run)
npm test                 # Vitest in watch mode
npm run prettier-fix     # Format everything
npm run outdated         # report Node, npm package and GitHub Actions updates
```

- Run `npm run build-lint-test` before considering a change done.
- The Node major is set in both `mise.toml` and `package.json`'s `devEngines.runtime`; change them together. `engines.node` is the minimum for consumers, and can stay lower.

## Structure

- `src/bin/`: CLI entry points (published as `dist/bin/*.js` via `package.json` `bin`). Responsible for argument parsing (yargs), file I/O, logging, and exit codes.
- `src/bin/utils/`: Helpers used only by the CLI entry points.
- `src/utils/`: Pure functions (no file I/O, no `process.exit`, no logging). Throw `Error`s on invalid input; the CLI catches them via `runCli`.
- `src/types/`: Shared types.
- `src/testValues/`: Test fixtures (excluded from `dist/`).
- `src/index.ts`: Public API. Only export what consumers need (currently the one function behind each CLI tool, plus `StringsObject`). Everything exported is a semver commitment.

## Conventions

- **One function per file**, with the file named after the function.
- **Default exports**: if a file exports a function with the same name as the file, use a default export (`const foo = …; export default foo;`). Re-export from `src/index.ts` with `export { default as foo } from "./utils/foo.js";`.
- **Small private helpers** used by only one function can stay unexported in that function’s file.
- **ESM with `.js` import specifiers** (e.g. `import foo from "./foo.js"`), including for lodash subpath imports (`lodash/merge.js`).
- **Don’t mutate arguments**. Note that lodash `merge` mutates its first argument; clone first (`structuredClone`) or use `lodash/fp/merge.js`.
- **CLI arguments** are required (no defaults that assume a consumer’s directory layout), and yargs is always used with `hideBin(process.argv)` and `.strict()`.
- **CLI scripts** start with `#!/usr/bin/env node` (not `tsx`, which consumers don’t have).
- **Prettier** is a peer dependency, so JSON output is formatted with the consuming project’s Prettier version and config.
- Keep object keys sorted (ESLint `perfectionist` rules enforce this; disable per-line with a comment only when unsorted order is the point, e.g. in a sorting test).

## Tests

- Vitest, in `*.test.ts` files next to the code they test.
- Test the public functions (and `getNestedStringsObjectDescriptions`, since the schema format is fragile) rather than every helper.
- Don’t wrap all of a file’s tests in a `describe` named after the file; use top-level `test` calls. Never use `it`.

## Compatibility

Output should stay byte-for-byte compatible with the original per-repo scripts (`src/scripts/{convertStringsCsvToJson,convertStringsJsonToCsv,syncAndSortStrings}.js` in the consumer repos), except for intentional changes listed in [CHANGELOG.markdown](CHANGELOG.markdown). When changing output, verify against those repos’ `src/strings/` files and update the changelog.

The strings JSON Schema is generated by ts-json-schema-generator from a `Strings` type whose top-level properties have types named `${Key}Strings`; `getNestedStringsObjectDescriptions` depends on that shape.

## Agent boundaries

`.claude/settings.json` makes Claude Code ask before editing `.npmrc` or `.claude/`, and before running `mise trust` or `git add`, `commit`, `push` or `config`. It denies edits to `.git/` outright: a hook dropped in `.git/hooks/` would run unconfined as the developer.

These rules are a backstop, not the boundary. Against the file tools (Read/Edit/Write) they're structural, but against Bash they only match command text, so `sh -c '…'` would slip past one. Never rephrase a command so it no longer matches a rule. A permission prompt isn't an invitation: only take the actions below when the user has asked for them, and treat a declined prompt as the user's decision. When a rule or gate blocks something, say what blocked it and hand over the exact command or edit for a human to run.

- **Only stage, commit or push when asked.** Otherwise leave changes in the working tree for a human to review. Don't rewrite history or change git config unless asked.
- **Only edit `.npmrc` or `.claude/` when asked.** `.npmrc` holds the supply-chain gates below, and `.claude/` holds these rules.
- **Keep `mise.toml` `[tools]`-only.** mise trusts a tools-only config automatically. Adding `[env]`, `[hooks]` or `[tasks]` makes it require `mise trust`, which lets the config run code, so only run `mise trust` when asked.
- **Node comes from mise's shims.** If `node --version` doesn't match `mise.toml`, stop and tell the user rather than prefixing commands with `mise exec`.

## npm supply-chain gates

npm enforces these itself, from `.npmrc` and `package.json`'s `devEngines` and `allowScripts`:

- **`min-release-age=1`**: installs only resolve versions published more than a day ago. Our own `@asl-19/*` scope is exempt. `npm ci` installs exactly what's in the lockfile, so it isn't affected.
- **`strict-allow-scripts=true`**: dependency install scripts run only if `allowScripts` approves them.
- **`allow-git=none`, `allow-remote=none`**: dependencies come from the npm registry only.
- **`engine-strict=true` + `devEngines`**: npm older than 11.17 ignores the keys above, so this refuses to run with one.

Every gate can be switched off for a single command with a CLI flag or an `npm_config_*` environment variable. That's an escape hatch for a human, not for an agent looking at a failed install:

- **Never loosen a gate for a command.** That means no `--min-release-age`, `--min-release-age-exclude`, `--before`, `--allow-scripts`, `--dangerously-allow-all-scripts`, `--no-strict-allow-scripts`, `--allow-git`, `--allow-remote` or `--no-engine-strict`, no `npm_config_*` equivalents, and the same for `npx`.
- **Don't edit `devEngines` or `allowScripts` in `package.json` to get past a gate.** The rest of `package.json` is fine to edit.
- **When a gate blocks an install, stop and report it:**
  - _Version too new:_ wait out the release-age window, or hand the install command to a human to run in their own terminal.
  - _Unapproved install script:_ name the package and what its script does. Approving it (`npm install-scripts approve <pkg>`) is a human decision.
  - _`EBADDEVENGINES`:_ the active Node or npm isn't the one from `mise.toml`, so see "Node comes from mise's shims" above.
