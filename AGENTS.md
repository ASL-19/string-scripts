# AGENTS.md

`@asl-19/string-scripts`: CLI tools (and the functions behind them) for converting strings JSON files to/from CSV for translators, and syncing strings JSON files. See [README.markdown](README.markdown) for usage.

## Commands

```sh
npm run build            # Compile src/ to dist/
npm run lint-test        # ESLint, Prettier, tsc, and Vitest (in parallel)
npm run build-lint-test  # What CI runs
npm run vitest-watch     # Vitest in watch mode
npm run prettier-fix     # Format everything
```

Run `npm run build-lint-test` before considering a change done.

## Structure

- `src/bin/`: CLI entry points (published as `dist/bin/*.js` via `package.json` `bin`). Responsible for argument parsing (yargs), file I/O, logging, and exit codes.
- `src/bin/utils/`: Helpers used only by the CLI entry points.
- `src/utils/`: Pure functions (no file I/O, no `process.exit`, no logging). Throw `Error`s on invalid input; the CLI catches them via `runCli`.
- `src/types/`: Shared types.
- `src/testValues/`: Test fixtures (excluded from `dist/`).
- `src/index.ts`: Public API. Only export what consumers need (currently the one function behind each CLI tool, plus `StringsObject`). Everything exported is a semver commitment.

## Conventions

- **One function per file**, with the file named after the function.
- **Default exports**: if a file exports a function with the same name as the file, use a default export (`const foo = …; export default foo;`). Re-export from `src/index.ts` with `export { default as foo } from "./utils/foo.js";`.
- **Small private helpers** used by only one function can stay unexported in that function’s file.
- **ESM with `.js` import specifiers** (e.g. `import foo from "./foo.js"`), including for lodash subpath imports (`lodash/merge.js`).
- **Don’t mutate arguments**. Note that lodash `merge` mutates its first argument; clone first (`structuredClone`) or use `lodash/fp/merge.js`.
- **CLI arguments** are required (no defaults that assume a consumer’s directory layout), and yargs is always used with `hideBin(process.argv)` and `.strict()`.
- **CLI scripts** start with `#!/usr/bin/env node` (not `tsx`, which consumers don’t have).
- **Prettier** is a peer dependency, so JSON output is formatted with the consuming project’s Prettier version and config.
- Keep object keys sorted (ESLint `perfectionist` rules enforce this; disable per-line with a comment only when unsorted order is the point, e.g. in a sorting test).

## Tests

- Vitest, in `*.vitest.ts` files next to the code they test.
- Test the public functions (and `getNestedStringsObjectDescriptions`, since the schema format is fragile) rather than every helper.
- Don’t wrap all of a file’s tests in a `describe` named after the file; use top-level `test` calls. Never use `it`.
- Vitest is pinned to v3: Vitest 4 crashes npm 11.4.2 during install (`Cannot read properties of null (reading 'edgesOut')`).

## Compatibility

Output should stay byte-for-byte compatible with the original per-repo scripts (`src/scripts/{convertStringsCsvToJson,convertStringsJsonToCsv,syncAndSortStrings}.js` in the consumer repos), except for intentional changes listed in [CHANGELOG.markdown](CHANGELOG.markdown). When changing output, verify against those repos’ `src/strings/` files and update the changelog.

The strings JSON Schema is generated by ts-json-schema-generator from a `Strings` type whose top-level properties have types named `${Key}Strings`; `getNestedStringsObjectDescriptions` depends on that shape.
